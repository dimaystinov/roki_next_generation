# Roki Next Generation

Программа робота Roki-2 для автономного и ручного футбола, адаптируемая к
новому образу головы на **Raspberry Pi CM4**: прямой libcamera, аппаратные
номера кадров Unicam и современный Python/OpenVINO с Intel NCS2.

Основа — [aleksey-yagubov/Roki_2_Soccer](https://github.com/aleksey-yagubov/Roki_2_Soccer),
коммит `32752dd8981c97b4f822702b689e14b599d4828c`. История исходного проекта
сохранена. Ниже описаны изменения относительно этой базы и текущие ограничения.

**Статус на 17 сентября 2026:** код и программные проверки подготовлены;
физическая проверка новых камеры/плагина NCS2 на CM4 ещё не выполнена.
В этом репозитории есть исходники, патч libcamera и материалы для сборщика
образа в [`buildroot/`](buildroot/README.md). **Готового прошиваемого образа
SD/eMMC здесь пока нет**: нужны Buildroot проекта, его defconfig, board files,
настройки загрузки/ядра и аппаратная проверка. Разработчик образа опубликует
код Buildroot и релиз после своих испытаний. Наличие `.blob` и `.mvcmd`
не означает наличие полной прошивки Roki или прошивки STM.

## Что изменено

| Область | Результат |
|---|---|
| Захват камеры | Picamera2 заменена прямыми Python bindings libcamera; один обработанный поток BGR для OpenCV |
| Номер кадра | Вместо вычисления по timestamp/FPS используется `rpi.UnicamSequence` из патча VC4 |
| Буферы | Четыре запрашиваемых буфера, отображение один раз, хранение последнего кадра, ограниченное ожидание snapshot |
| IMU головы | Точный ID передаётся в `GetIMUFrame`, включая 0 и работу без фонового vision stream |
| Перезапуск камеры | Остановка старого потребителя и камеры; существующий STM-канал сохраняется |
| Управление камерой | `ExposureTime`, `AnalogueGain`, `FrameDurationLimits`, `AwbEnable`, `AeEnable` через libcamera controls |
| RTSP | Встроенный GstRtspServer удалён; остаются `null` и `imshow` |
| Ручное видео | Существующий RTP/JPEG через GStreamer core и UDP сохранён |
| NCS2 | Добавлен отдельный нативный MYRIAD blob-плагин для OpenVINO 2026.0; старый Python/runtime на голове не нужен |
| Модель | Восстановлены исторические веса и скомпилирована настоящая `ball.blob`; качество на поле ещё не проверено |
| Отказ нейросети | Приватный дочерний процесс на том же Python, таймауты, отключение при сбое и цветовое распознавание |
| Локализация | Выполнен аудит и добавлены воспроизводящие тесты; найденные ошибки алгоритмов пока не исправлены |
| Утилиты | Камерные тесты, просмотр, калибровки и ручной сервер переведены на общий адаптер камеры |
| Образ | В `buildroot/` включены патч, исходники плагина, модель, USB firmware, инструкции и контрольные суммы |

## Камера и синхронизация с IMU

### Требуемая библиотека

Целевая версия — `libcamera 0.7.2+rpt20260817`, Raspberry Pi VC4/CM4,
с патчем [`0001-rpi-unicam-sequence.patch`](buildroot/0001-rpi-unicam-sequence.patch).
Это дополнение образа: в немодифицированной библиотеке данного тега поля
`libcamera.controls.rpi.UnicamSequence` нет.

Патч берёт `bayerFrame.buffer->metadata().sequence` у внутреннего Bayer-буфера
Unicam и добавляет его в metadata соответствующего request перед ISP.
Он не копирует пиксели и не требует RAW-потока приложения. Образ должен
содержать согласованно пересобранные libcamera, RPi IPA и Python bindings.
Подробности: [интеграция патча](buildroot/LIBCAMERA_PATCH_RU.md).

### Запуск и конфигурация

[`Soccer/Vision/camera.py`](Soccer/Vision/camera.py) получает
`CameraManager.singleton()`, выбирает и захватывает камеру, формирует один
`StreamRole.VideoRecording`, проверяет конфигурацию, выделяет буферы и
ставит requests в очередь. Поток захвата обрабатывает завершённые requests.

| Параметр | Значение / поведение |
|---|---|
| Камера | Индекс 0 по умолчанию |
| Размер | 800 × 650, задаётся существующим `camera_lores` |
| Формат | libcamera `RGB888`, отображаемый в V4L2 `BGR24`: байты B,G,R, готовые для OpenCV |
| Буферы | Запрашиваются 4; используются реально выделенные после проверки конфигурации |
| Длительность кадра | 16700 мкс по умолчанию; фактический режим ограничивается сенсором |
| Выдержка | `ExposureTime`, целое число микросекунд |
| Аналоговый gain | `AnalogueGain`, число с плавающей точкой |
| Автоэкспозиция | `AeEnable=False`, когда заданы и выдержка, и gain |
| Баланс белого | `AwbEnable=bool(neural)` при запуске |
| Ожидание snapshot | 3 секунды по умолчанию |

`snapshot()` берёт кадр из работающего потока и возвращает
`(bgr_array, unicam_sequence)`. Он **не запускает одиночную съёмку с остановкой
камеры**. Адаптер хранит последний завершённый request и переиспользует старые;
задержавшийся потребитель получает актуальный кадр с настоящим пропуском ID.

Учитывается stride, синхронизируется CPU-доступ к DMA-BUF. Перед возвратом
выполняется одна копия BGR, чтобы последующее переиспользование камерного
буфера не изменяло изображение у потребителя. Дополнительного demosaic или
преобразования RGB/BGR на CPU нет. `set_controls({...})` применяет изменения
на следующем повторно поставленном request; изменение не обещает мгновенный
эффект на уже экспонируемый кадр. `stop()` останавливает поток и освобождает
requests, отображения и камеру.

### ID кадра и STM

`UnicamSequence` не заменяется на `Request.sequence`, ISP sequence или
пересчёт времени/FPS. Номер 0 допустим, пропуски сохраняются, аппаратный
32-битный счётчик может обернуться. Первый полученный кадр не обязан быть 0.
При отсутствии поля приложение сообщает ошибку — синтетического ID нет.

В [`class_stm_channel.py`](Soccer/Motion/class_stm_channel.py) переданный
номер всегда используется для `GetIMUFrame`, независимо от `camera_streaming`.
`GetIMULatest` вызывается только без номера; недоступный индексированный
образец не подменяется последним. При старте камеры сбрасывается история
стробов. `Glob.camera_reset()` сначала останавливает старый потребитель,
затем камеру; канал STM, используемый движением, не заменяется новым объектом.

Электрическое соответствие счётчиков STROBE и Unicam ещё нужно проверить
на роботе. Произвольный программный сдвиг на +1/+2 не добавлен.
Полное описание: [LIBCAMERA_UNICAM_SYNC.md](LIBCAMERA_UNICAM_SYNC.md).

## Нейросеть OpenVINO и NCS2

### Нативный плагин

Основной путь интеграции теперь — [форк OpenVINO](https://github.com/dimaystinov/openvino),
собранный вместе с плагином из `src/plugins/intel_myriad/`:
`-DENABLE_INTEL_MYRIAD=ON`. Его база — OpenVINO **2026.5.0**;
[инструкция сборки](https://github.com/dimaystinov/openvino/blob/master/README_NCS2_RU.md).
Новый runtime и его Python bindings проверяются вместе. `MYRIAD` регистрируется
автоматически; приложение не пытается зарегистрировать его повторно.
При явно заданном `ROKI_NCS2_PLUGIN` приложение создаёт Core с отдельной
XML-конфигурацией выбранной библиотеки, исключая конфликт регистраций.

Ниже сохранено описание **первого standalone-комплекта для 2026.0**.
Его нельзя смешивать с runtime 2026.5; для форка плагин собирается из самого
форка, а не из старого `buildroot/openvino-ncs2/`.

[`buildroot/openvino-ncs2/`](buildroot/openvino-ncs2/README_RU.md) содержит
исходники плагина, который регистрируется как `MYRIAD` в OpenVINO **2026.0.0**.
Из OpenVINO **2022.3.2** используются исходники транспортных mvnc/XLink;
старый OpenVINO runtime и его Python bindings на голове не загружаются.
Версии runtime и developer headers должны совпадать: это внутренний C++ API,
совместимость с произвольным последующим OpenVINO не заявляется.

Плагин импортирует статический MYRIAD `.blob` формата 6.0 через
`Core.import_model`. **Компиляция XML/ONNX новым плагином пока не реализована.**
Готовый blob создаётся заранее инструментом
[`offline/compile_ball.cpp`](buildroot/openvino-ncs2/offline/compile_ball.cpp)
с C++ compiler OpenVINO 2022.3.2 на машине подготовки модели.

Проверяются структура blob, размеры, формы, типы, смещения и padding.
Передача USB сериализуется, чтобы не смешивать ответы requests; ошибка
помечает транспортную сессию неисправной. В приложении один NCS2 и одна
модель, request переиспользуется. Поддержка нескольких физических устройств
и качество работы на реальном NCS2 ещё требуют испытаний.

### Модель и обработка

В комплекте исторический кандидат `orange_ball_on_green_only` из коммита
`ad372a887a6b62f51c2cba7a7156363dc642c882` исходного проекта: XML, BIN и
скомпилированная `ball.blob`. Вход blob — U8 NHWC `[1,640,640,3]`, выход —
FP32 `[1,25200,7]`. BGR → RGB, деление на 255 и преобразование layout встроены
в граф. В Python остаются letterbox и постобработка YOLOv5.

Исправлены использование `xywh` для `cv2.dnn.NMSBoxes`, выбор наиболее
уверенной допустимой детекции, пересчёт координат с учётом реального
масштаба/полей letterbox и отбрасывание центров в padding. По историческому
коду используются классы ball=0, basket=1. Это не подтверждение актуальности
обучения: перед матчем нужны реальные изображения поля и оценка качества.

### Если NCS2 отключится

[`Neural`](Soccer/Vision/neural.py) запускает приватный дочерний процесс
[`neural_worker`](Soccer/Vision/neural_worker.py) через тот же `sys.executable`.
Только ребёнок загружает OpenVINO. Такое разделение защищает основной
процесс от нативных падений и зависаний; старого Python-воркера или отдельного
устанавливаемого сервиса нет.

- Один mmap на 16 MiB хранит кадр: на Linux используется анонимный memfd в RAM.
  Передача добавляет одну копию BGR, без преобразования цвета.
- Socketpair передаёт небольшие управляющие сообщения и центр объекта.
  Публичного сетевого порта нет; номер запроса проверяется.
- В обработке один кадр. Очередь и кэш устаревших результатов отсутствуют.
- При исключении USB, выходе ребёнка, разрыве IPC или таймауте детектор
  отключается, возвращает `(0, 0)` и сохраняет причину в `neural.error`.
- Поиск мяча и оценка скорости переходят к цветовым алгоритмам в том же
  отказавшем вызове, с новым снимком. Последующие вызовы не ждут NCS2 заново.
- Автопереподключения во время матча нет. После восстановления устройства
  явный `glob.neural_vision_enable()` закрывает прежний процесс и создаёт новый.
- Завершение ребёнка не ждёт нативных деструкторов. На Linux предусмотрено
  завершение ребёнка при смерти родителя.

| Переменная окружения | По умолчанию |
|---|---|
| `ROKI_NCS2_BLOB` | `/usr/share/roki/ball.blob` |
| `ROKI_NCS2_PLUGIN` | Автоматический MYRIAD; при отсутствии регистрации — `libopenvino_ncs2_plugin.so` |
| `NCS2_FIRMWARE_DIR` | Рекомендуемый путь образа: `/usr/share/roki/firmware` |
| `ROKI_NCS2_TIMEOUT` | 1 с на ответ inference |
| `ROKI_NCS2_STARTUP_TIMEOUT` | 15 с на готовность ребёнка |

Ожидание завершения ребёнка добавляет до 0.2 с. Это ограничения ожидания IPC,
а не жёсткого реального времени ОС. Таймаут нужно подобрать по измерениям
на CM4, включая первый кадр. Нативный транспорт имеет собственный таймаут
10 с; супервизор приложения может прервать ребёнка раньше.

Подробности и сценарии тестирования:
[NCS2_RESILIENCE_RU.md](docs/NCS2_RESILIENCE_RU.md).

## Видео и ручное управление

Встроенный GstRtspServer, класс `RtspDisplay` и настройка `DISPLAY_RTSP_PORT`
удалены. В [`display.py`](Soccer/Vision/display.py) остаются:

- `null` — по умолчанию, для головы без экрана;
- `imshow` — локальные OpenCV-окна.

Выбор: `ROKI_DISPLAY_BACKEND` или `DISPLAY_BACKEND` в параметрах.
Устаревшее/неизвестное имя приводит к `null`.

[`tools/manual_msgpack_server.py`](tools/manual_msgpack_server.py) сохраняет
существующее управление MessagePack/UDP и адресный RTP/JPEG видеопоток:
GStreamer core, `appsrc`, `videoconvert`, `v4l2jpegenc`, `rtpjpegpay`, `udpsink`.
Удаление RTSP не удаляет эти зависимости при использовании ручного видео.
Обычный адаптер камеры и нейросеть от GStreamer не зависят.

Текущий порт управления — 8093, видео — 5004; параметры доступны в `--help`.
Существующий сервер — основа будущего протокола. Общий протокол запуска
робота, матчевой телеметрии, отладки, калибровок и просмотра локализации
**ещё не спроектирован**. Новых обещанных команд для него здесь нет.
Видео и калибровка должны разделять существующего владельца камеры, а не
открывать конкурирующий захват. См. [STREAMING_NOTES.md](STREAMING_NOTES.md).

## Проверка локализации

Выполнен аудит одометрии, визуальных наблюдений и particle filter.
[LOCALISATION_REVIEW_RU.md](docs/LOCALISATION_REVIEW_RU.md) содержит источники,
последствия и тесты. Найденные ошибки не следует считать исправленными:

- В Real defaults отсутствует обязательный `USE_PARTICLE_FILTER`; без
  локального значения инициализация может завершиться `KeyError`.
- В гауссовых весах неверно расставлены скобки относительно `sigma²`.
- При выключенной прямой оценке координат пустой список записывается в
  shared array длины 3.
- Повторные yaw-коррекции накапливаются до ответа PF.
- При заполнении очереди одометрии запись попадает в слот, который не читает
  потребитель.
- Усреднение yaw около ±π может дать направление около 0.
- Вход обычного goalkeeper в `main_killable_all.py` не получает полный
  комплект vision/local; согласованность shared-наблюдений также требует работы.

Есть 10 strict-xfail проверок известных дефектов; это не десять независимых
ошибок. Поэтому готовность к автономному матчу этим обновлением не заявляется.
В ручном сервере `DummyLocal` остаётся заглушкой, а не оценкой положения.

## Подготовка образа и размещение файлов

Начать с [buildroot/README.md](buildroot/README.md). Каталог содержит материалы
для существующего сборщика, **не полный Buildroot external tree**.

На голове нужны Python образа, numpy, OpenCV, прямые Python bindings libcamera
с патчем и аппаратные bindings `Roki` для STM. Для NCS2 дополнительно нужны
OpenVINO из форка с его плагином (либо согласованный standalone 2026.0), libusb
и USB firmware. Для ручного управления нужны msgpack и компоненты GStreamer;
для существующих кнопок запуска — evdev. Нельзя переносить собранную на macOS
библиотеку в Linux-образ; используются target toolchain и staging sysroot.

| Файл комплекта | Путь в целевом образе |
|---|---|
| Собранный `libopenvino_ncs2_plugin.so` | `/usr/lib/` или соответствующий target libdir |
| `buildroot/ball.blob` | `/usr/share/roki/ball.blob` |
| `buildroot/usb-ma2x8x.mvcmd` | `/usr/share/roki/firmware/usb-ma2x8x.mvcmd` |
| Код программы | Например `/opt/roki/`; это рекомендуемый путь, не установленный сервис |
| Локальные параметры и калибровки | `Init_params/local/` установленной программы, с возможностью записи |

Сначала сохраните параметры конкретного робота. При чтении одноимённого
файла `Init_params/local/` имеет приоритет над `defaults/`; это подмена файла,
не автоматическое слияние всех JSON-ключей. См. [Init_params/README.md](Init_params/README.md).
В выбранном Real-файле параметров нужно явно определить `USE_PARTICLE_FILTER`;
включать PF до исправления найденных дефектов недостаточно для рабочей локализации.

USB firmware загружается плагином в NCS2 при открытии устройства. Её не
записывают как образ eMMC CM4 и не прошивают ею STM. Инструкции записи
конкретного SD/eMMC image должны приходить из board-конфигурации Buildroot;
в этом комплекте такого image ещё нет.

## Проверки и запуск

### На машине разработки, без робота

Понадобятся Python, numpy, pytest и OpenCV. Команды выполняются из корня:

```sh
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q tests
```

Текущий результат: **60 passed, 10 xfailed**. Камера и аппаратный OpenVINO API
в этих тестах заменены контролируемыми реализациями. Для проверки изоляции
запускаются настоящие дочерние Python-процессы с ошибками/зависаниями/выходом.
Чтобы увидеть ожидаемые дефекты локализации как ошибки:

```sh
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q --runxfail tests/test_localisation_audit.py
```

Это намеренно непроходящий аудит, не команда приёмки исправленной локализации.
C++ parser и интеграция настоящего OpenVINO с тестовым USB transport проверяются
отдельно через CTest, см. [плагин](buildroot/openvino-ncs2/README_RU.md).

### На CM4, сначала отдельные проверки оборудования

При остановленных других владельцах камеры:

```sh
python3 -c 'import libcamera; print(libcamera.controls.rpi.UnicamSequence)'
python3 tools/test/check_libcamera.py --frames 100 --restarts 2
```

Проверяются размер `(650,800,3)`, тип U8, последовательность ID с сохранением
пропусков и перезапуски. Эти команды не открывают канал Roki и не двигают
сервоприводы. Отдельно сверяются BGR по цветной мишени и совпадение с STM/IMU.

Для NCS2 после сборки/установки файлов:

```sh
export NCS2_FIRMWARE_DIR=/usr/share/roki/firmware
python3 tools/test/check_openvino_ncs2.py \
  --plugin /usr/lib/libopenvino_ncs2_plugin.so \
  --model /usr/share/roki/ball.blob --iterations 100
```

Без `--inputs` используются нулевые тензоры: это проверка исполнения, не
распознавания мяча. `--inputs samples.npz` принимает `input_0`, `input_1`, …
нужных форм/типов. Диагностический скрипт вызывает плагин напрямую; изоляция
сбоев относится к `Neural` приложения, а не к этому отдельному probe.
После этого нужны кадры поля, измерение задержек и извлечение NCS2 во время
работы приложения с проверкой продолжения камеры, управления и цветового зрения.

### Запуск программы

Клонирование:

```sh
git clone https://github.com/dimaystinov/roki_next_generation.git
cd roki_next_generation
```

После подготовки образа и локальных параметров существующий запуск с кнопками
выполняется через `python3 main.py`. Доступные роли и аппаратные зависимости
определяются существующими `main_killable*.py`; замечания аудита по goalkeeper
и конфигурации остаются актуальными. Ручной сервер запускается отдельно:

```sh
python3 tools/manual_msgpack_server.py --help
```

Одновременно запускать два владельца камеры не нужно. Этот README не
подменяет настройку сервоприводов, STM firmware и проверку локальных калибровок.

## Что ещё нужно сделать

1. Интегрировать комплект в конкретный Buildroot проекта, собрать образ CM4
   и проверить загрузку с нужного носителя.
2. На роботе подтвердить захват libcamera, номер Unicam ↔ STM и перезапуски.
3. Проверить USB boot, настоящую сеть на NCS2, отключение/повторное подключение,
   задержки, потребление ресурсов и качество распознавания.
4. Исправить подтверждённые дефекты локализации и прогнать записанные данные поля.
5. Спроектировать общий MessagePack-протокол для запуска, телеметрии, отладки,
   калибровок, локализации и ручного управления.

Исторические режимы других дисциплин оставлены, но текущий приоритет —
автономный и ручной футбол. Сборка библиотеки и программные тесты не означают
подтверждённой аппаратной готовности всей системы.
